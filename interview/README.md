# 모의 라이브 코딩 연습

라이브 코딩은 "코드를 짜는 시험"이 아니라 **"생각을 말로 꺼내면서 짜는 시험"**이다.
정답을 내는지보다 과정을 본다. 못 풀어도 붙는 사람이 있고, 풀어도 떨어지는 사람이 있다.

```
interview/
├── README.md                          이 문서 — 방법론 + 연습 기록
├── pom.xml
└── src/
    ├── main/java/interview/
    │   ├── MostActiveUser.java        #1  Map + Set 으로 개수 세기
    │   ├── MeetingOverlap.java        #2  구간 겹침, 정렬로 O(n²) → O(n log n)
    │   ├── BestSeller.java            #3  Map<String, Integer> 합계, 초기값 함정
    │   ├── SimplifyPath.java          #4  Stack — 경로 정규화, 빈 Stack pop 함정
    │   └── WaitingTimes.java          #5  Queue 개념 + 누적 합, "Queue 객체가 진짜 필요한 때"
    └── test/java/interview/           각 문제의 엣지 케이스 테스트
```

```bash
cd interview
mvn test
```

## 1. 면접관이 보는 것

| 좋게 보이는 행동 | 나쁘게 보이는 행동 |
|---|---|
| 시작 전에 문제를 되묻는다 | 바로 타이핑 시작 |
| "먼저 단순하게 O(n²)으로 하고 개선하겠습니다" | 처음부터 최적해 찾느라 침묵 |
| 막히면 "~부분이 헷갈리는데 ~방향으로 생각 중입니다" | 막히면 침묵 |
| 다 짜고 예시 입력으로 손 추적 | 짜자마자 "됐습니다" |
| 문법 기억 안 나면 "확인하겠습니다"하고 넘어감 | 문법 틀릴까 봐 얼어붙음 |

**문법 틀리는 건 거의 감점이 아니다. 침묵이 감점이다.**

## 2. 매번 쓰는 틀

```
① 문제 되묻기     엣지 케이스 2~3개 (아래 체크리스트), 출력 형식, 입력 크기
② 예시 손풀이     주어진 예시를 손으로 따라가며 답 확인
③ 접근법 + 복잡도  "먼저 단순하게 O(n²)로, 그다음 개선" 식으로 말하기
④ 코드            중계하면서. 문법 틀려도 됨
⑤ 추적            예시 입력으로 코드를 한 줄씩 따라가기
⑥ 개선점          "실무라면 ~도 고려하겠습니다"
```

막혔을 때 할 말: **"지금 ~부분이 헷갈립니다. ~방향으로 생각 중인데 힌트 주실 수 있을까요?"**

## 3. 엣지 케이스 — 체크리스트로 묻기

엣지 케이스는 "보통 입력"이 아니라 **가장자리 입력**이다. 코드는 정상 범위에서는 잘 돌다가 끝자락에서 깨진다.
실무 버그의 절반(`NullPointerException`, `IndexOutOfBounds`, 0으로 나누기)이 여기서 난다.

면접에서 먼저 묻는 이유 두 가지:
1. **문제가 정해진다** — `<`냐 `<=`냐, null을 돌려줄지 예외를 던질지. 모르면 코드를 못 쓴다.
2. **실무 습관이 보인다** — 요구사항 받고 "빈 값이면요?"를 묻는 사람과 안 묻는 사람은 코드 품질이 다르다.

### 체크리스트 — 문제의 모든 명사·숫자에 기계적으로 적용

```
① 없으면?        0개, 빈 문자열, null
② 하나면?        원소 1개 — 비교할 상대가 없는 상황
③ 경계가 닿으면?  ★ 같은 값(동점) ★, 딱 붙은 값, 최솟값·최댓값, 역순, 음수, 중복
```

**배열·목록이 나오면 ①②는 소재와 무관하게 무조건.** #3에서는 물었고 #4, #5에서 연속으로 빠짐 —
소재가 바뀌면 체크리스트가 날아가는 패턴. "배열 → 빈 것? 하나?"를 반사로.

창의력이 아니라 **체크리스트를 돌리는 것**이다.
③의 **동점**은 #1, #3에서 두 번 연속 빠뜨린 항목 — "최대/최소를 구하라"는 문제엔 항상 있다.

### 두 문제에 적용한 예

**#1 로그 → 사용자**

| 명사 | ① 없으면 | ② 하나면 | ③ 경계 |
|---|---|---|---|
| 로그 배열 | 빈 배열 → null? 예외? | 한 줄 → 그 사용자 | — |
| 사용자 | — | 한 명 | **동점**이면? |
| 페이지 | — | — | 중복 (문제에 명시) |
| 문자열 형식 | 공백 없는 줄? | — | 공백 두 개? |

**#2 예약 겹침**

| 명사 | ① 없으면 | ② 하나면 | ③ 경계 |
|---|---|---|---|
| 예약 배열 | 빈 배열 → false | 1개 → false | 정렬돼 있나? |
| 시작·종료 | — | — | **딱 붙은 것**, 같은 것, 종료 < 시작 |

표로 그리면 #1의 "동점", #2의 "딱 붙은 것"이 바로 튀어나온다. 이 둘이 각 문제의 유일한 함정이었다.

### 문제가 이해 안 되면

**"문제를 이해 못 하겠습니다"를 바로 말한다.** ①의 가장 기본형. 이해 안 된 채 코드로 가는 게 최악.
면접관은 다시 설명해 주고, 그 뒤에 예시를 **손으로 따라가며** (②) 이해했는지 확인한다. (#4)

### 면접에서 말하는 법

전부 물을 필요 없다. **2~3개만, 시작 전에, 한 번에**:

> "시작 전에 몇 가지 확인하겠습니다. 배열이 비어 있을 수 있나요?
> 종료가 시작보다 앞인 잘못된 입력은 없다고 봐도 될까요?
> 11시에 끝나고 11시에 시작하는 건 겹친 걸로 보나요?"

30초. 면접관이 "그건 없다고 가정하세요"라고 하면 그대로 받아들이고 넘어간다. 물었다는 것 자체가 점수다.

**깊이 조절**: 요구사항 회의에서는 "이 입력은 누가 만드나, 에러로 알려야 하나"를 끝까지 파는 게 맞지만,
라이브 코딩은 **한 문장 확인 → 넘어가기**가 리듬. 네 개를 깊이 파면 40분 중 10분이 간다. (#4)

### 실무에서는 = 테스트 케이스

같은 체크리스트가 그대로 테스트 목록이 된다. `MeetingOverlapTest`:
```
빈_배열 / 예약_하나 / 딱_붙은_것은_겹치지_않는다 / 완전히_같은_예약은_겹친다 / 역순으로_들어와도_된다
```
면접의 엣지 케이스 질문 = 실무의 테스트 케이스. 같은 근육이다.

### 흔한 함정 유형

| 유형 | 예 |
|---|---|
| **off-by-one** | `<` vs `<=`, `i < n` vs `i <= n`, 0부터 vs 1부터 |
| **빈 컬렉션** | `list.get(0)`, `max()` 초기값, 평균 구할 때 0으로 나누기 |
| **null** | `null.length()`, Map에 없는 키 `get` → null |
| **중복** | Set으로 처리했나, 동점 처리 규칙 |
| **경계 수치** | `Integer.MAX_VALUE + 1` 오버플로, 음수 인덱스 |
| **순서** | 정렬 가정했는데 안 돼 있음, 역순 입력 |
| **구간** | 한쪽이 다른 쪽을 통째로 감싸는 경우 (#2의 함정) |
| **초기값** | `max`를 `0`에서 시작 → 전부 음수면 아무것도 안 잡힘. `Integer.MIN_VALUE` 또는 "첫 번째는 무조건 채택" (#3의 함정) |
| **빈 Stack/Queue** | 비어 있는데 `pop`/`poll` → 예외(`NoSuchElementException`, NPE 아님). `isEmpty()` 먼저 (#4의 함정) |

## 4. 반사적으로 나와야 하는 자료구조 짝

| 문제에서 이런 말이 나오면 | 바로 떠올릴 것 |
|---|---|
| "중복 제거", "이미 봤는지" | `Set` (`HashSet`) |
| "~별로 묶어서", "이름으로 찾아서" | `Map` (`HashMap`) |
| "개수 세기", "빈도", "합계" | `Map<K, Integer>` + `getOrDefault`+`put` 또는 `merge(k, v, Integer::sum)` |
| "가장 큰 k개", "상위 N" | `PriorityQueue` (힙) |
| "순서대로 처리", **"가장 먼저 넣은 것"** | `Queue` (`ArrayDeque`) — FIFO, 줄 서기 |
| "괄호", "되돌리기", **"가장 최근에 넣은 것"** | `Stack` (`ArrayDeque`) — LIFO, 접시 쌓기 |
| ↑ 둘은 정반대. 이름 말하기 전에 "가장 최근? 가장 먼저?" 한 번 자문 (#4에서 혼동, #5에서 성공) | |
| "지금까지의 합", "앞사람들 합", "잔액", "구간 합" | **누적 합(prefix sum)** — 변수 하나 들고 한 바퀴. SQL `SUM() OVER (ORDER BY)` |
| 문제에 시계가 없으면 | 시뮬레이션이 아니라 **산수**. 실시간으로 깎지 않는다 (#5) |

**이름 다음 단계**: 자료구조 이름을 맞히는 것 → **"지금 그 객체가 실제로 필요한가"** 판단.
#5는 개념이 Queue인데 코드에 Queue 객체가 없다 — 배열을 0번부터 도는 것이 이미 FIFO라서.
Queue 객체가 진짜 필요한 때: 요청이 실행 중에 계속 들어옴 / 처리자가 여럿 / 우선순위(→ PriorityQueue).
| "정렬된 상태 유지", "범위 검색" | `TreeMap` / `TreeSet` |
| "최단 거리", "몇 단계 만에" | BFS |
| "모든 경로", "연결돼 있나" | DFS |
| **"O(n²)인데 빨라지려면?"** | **정렬** 아니면 **HashMap** — 이 둘이 90% |

## 4-1. 자료구조 고르는 법 — "조합"보다 "선택"이 먼저

모든 자료구조는 **한두 가지 연산을 빠르게 하려고 다른 걸 포기**한 것. 고르는 질문은 하나:
**"이 문제에서 반복적으로 하는 연산이 뭔가?"**

| 반복하는 연산 | 자료구조 | 포기한 것 |
|---|---|---|
| 키로 찾기 / 있나 확인 | HashMap / HashSet | 순서 |
| 가장 최근 것 꺼내기 | Stack | 중간 접근 |
| 가장 먼저 것 꺼내기 | Queue | 중간 접근 |
| 가장 작은/큰 것 계속 꺼내기 | Heap (PriorityQueue) | 정렬된 순회 |
| 정렬 유지 + 범위 검색 | TreeMap / BST | HashMap보다 느림 |
| 인덱스 접근, 순서대로 | 배열 / ArrayList | 중간 삽입 |
| 연결 관계 따라가기 | Graph (Map + List) | — |

**고르는 순서**
```
1. 손풀이 표를 그린다                   → 반복되는 동작이 보인다
2. 그 동작을 한 문장으로               → "이름으로 찾는다", "최근 것을 취소한다", "앞사람 합을 안다"
3. 위 표에서 맞는 줄                   → 자료구조 이름
4. 그 객체가 진짜 필요한가             → #5처럼 변수 하나로 되면 그걸로 (초보는 많이, 숙련자는 적게 쓴다)
5. 동작이 둘이면 둘을 조합             → #1처럼 Map<K, Set<V>>
```

**다섯 문제에 적용**

| 문제 | 반복한 연산 | 선택 | 조합? |
|---|---|---|---|
| #1 | 이름으로 찾기 + 중복 제거 | Map + Set | 조합 (2개) |
| #2 | 앞 것과 비교 | 정렬 후 배열 | 단일 |
| #3 | 이름으로 찾아서 더하기 | Map | 단일 |
| #4 | 최근 폴더 취소 | Stack | 단일 |
| #5 | 순서대로 누적 | 배열 (개념은 Queue) | 없음 — 변수 하나 |

**자주 나오는 조합 (이 7개가 90%)**

| 조합 | 하는 일 | 예 |
|---|---|---|
| Map + Set | 그룹별 중복 없는 목록 | #1 |
| Map + List | 그룹별 순서 있는 목록 | 그래프 인접 리스트, 부서별 직원 |
| Map + Integer | 세기 / 합계 | #3, 단어 빈도 |
| 정렬 + 한 바퀴 | 인접 비교 | #2, 중복 찾기, 구간 병합 |
| Heap + Map | "가장 ~한 것"을 계속 꺼내되 정보도 필요 | 다익스트라, 상위 K |
| HashMap + LinkedList | 찾기도 빠르고 순서도 유지 | LRU 캐시 (유명 면접 문제) |
| Stack 두 개 | 되돌리기 + 다시 실행 | undo / redo |

**오해 두 가지**
- "고급 자료구조를 쓰면 좋은 코드" → 반대. 가장 단순한 걸로 되면 그게 정답. 안 쓴 이유보다 쓴 이유를 설명해야 한다.
- "자료구조를 외워야 한다" → 외울 건 위 첫 표 7줄. 구현 세부는 한 번 본 걸로 충분. "HashMap이 왜 O(1)?"에 두 문장이면 된다.

## 5. 문제 선정 기준 (#4 이후)

#4(경로 정규화)는 LeetCode 71번으로, 실무에서는 `Path.normalize()` / Spring `cleanPath` 를 호출하지 직접 짜지 않는다.
Stack 반사와 엣지 케이스 밀도 때문에 골랐지만 **실무자 입장에서는 의아한 문제**였다.

- SI·MyBatis 계열 면접: SQL, Java 기초, Spring 개념 + "로그 읽어서 묶고 세기" 수준의 라이브 코딩 (#1, #3 유형)
- 제품 회사·외국계: LeetCode 유형도 나옴 (#4 유형)
- 그래도 **실제로 나오면 한 번 본 게 덜 당황스럽다** → 앞으로는 **번갈아**:
  - 홀수 회: 실무 소재 (로그, 주문, 일정, 그룹핑) — 일상 코드를 말로 설명하는 연습
  - 짝수 회: LeetCode 빈출 고전 (두 수의 합, 괄호 짝, 구간 병합, 애너그램 묶기, BFS 미로, LRU 캐시 …) — 낯선 문제에 틀을 적용하는 연습

LeetCode형 문제를 실제로 받았을 때 할 말:
> "이건 `Path.normalize()`가 해 주는 로직인데, 직접 구현해 보라는 의도로 이해하면 될까요?"
→ 실무에서 뭘 쓰는지 안다 + 문제 의도에 맞춰 풀겠다, 둘 다 전달된다.

## 6. 경험 질문 — 라이브 코딩보다 합격을 더 좌우한다

#5에서 **MQ로 금융 거래 부정 검사 프로그램**을 만든 경험이 나왔다.
"요청이 계속 들어오고 처리자가 꺼내 가는" 구조 = Queue를 실제 운영해 본 것. 이론으로 아는 사람과 완전히 다르게 보인다.

면접 전에 복원해 둘 네 줄 (모든 경험에 같은 틀):

```
무엇을:   거래 내역 → MQ → 부정 거래 검사기
규모:     초당/일당 몇 건, 허용 지연 몇 ms (대략이라도)
문제:     뭐가 느렸나 — 큐가 쌓였나, 검사 로직? DB 조회? 외부 API?
해결:     뭘 바꿨나 — 배치 처리, 캐시, 컨슈머 증설, 인덱스, 비동기 전환 …
```

"자세한 건 잊었다"면 그때 코드·문서·장애 티켓을 다시 열어 보고 네 줄만 채운다. 숫자 하나가 있으면 신뢰도가 다르다.

## 7. 명세·검증 연습 — 역할을 바꾼 모의

### 왜

바이브 코딩에서 AI가 "지시를 못 알아듣고 빠뜨리는" 원인은 대부분 **요구사항이 암묵적**이어서다.
빈 값, 동점, 순서, 에러 정책을 안 적으면 AI는 제멋대로 정한다 (사람 신입도 같다).
→ AI 시대 실력 = **요구사항을 빠짐없이 명시** + **남이 짠 코드를 읽고 틀린 곳 찾기** + **테스트로 증명**.
라이브 코딩 연습의 "엣지 케이스 묻기 / 손풀이 추적 / 왜 그 구조냐 설명"이 정확히 같은 근육.

자료구조·알고리즘은 **지금 수준에서 유지**(선택할 수 있고, O(n²)을 알아보고, 복잡도를 말할 수 있으면 됨).
더 팔 곳은 DB 설계·쿼리 튜닝·트랜잭션·시스템 설계. 비중은 **명세·검증 > 알고리즘**.

### 규칙

```
1. 내가 지시문을 쓴다 — 실무에서 AI/후임에게 시키듯, 평소 말투·평소 분량으로
2. AI는 적힌 대로만 구현. 안 적힌 건 제멋대로 정하고, 뭘 정했는지 "숨긴 목록"에 적어 둔다
3. 내가 코드를 검토 — 빠진 것 / 잘못 정한 것 / 버그
4. 숨긴 목록 공개 → 잡은 것 vs 놓친 것
5. 지시문을 고쳐 다시 쓴다 (2라운드)
```

소재는 `board-fullstack`에 실제 기능 추가 (검색, 댓글, 페이징, 조회수 …). 장난감이 아닌 진짜 코드를 검토한다.

### 기록

#### 명세·검증 #1 — "스프링 프레임워크를 최신버전으로 업그레이드 및 maven에서 gradle로 변경"

**AI가 제멋대로 정한 것 16개 중 핵심 5개**

| 결정 | AI의 선택 | 잡았나 |
|---|---|---|
| "최신" = GA만? 마일스톤도? | GA 4.1.1 | ✗ |
| 메이저(3→4) 올려도 되나 — 호환성 | 올림 | ✗ |
| README 실행법(`./mvnw`) 고칠지 | 안 고침 → 문서·코드 불일치 | ✗ |
| application.yml 설정이 Boot 4에서 유효한지 | 안 봄 | ✗ |
| **검증 중 발견한 `/h2-console` 404 회귀** | 안 고침 | ✗ |
| dependency-management 플러그인 → platform() | Boot 4에서 깨져서 변경 | △ 알아챘으나 "빠졌다"로 결론 |

**내가 본 것**: `build.gradle` 한 파일. 두 지적 모두 의심은 정당했으나 결론이 반대 (import는 쓰이고 있었고, 플러그인은 일부러 뺀 것).

**드러난 패턴**
- 바뀐 파일만 본다 → **안 바뀌어서 문제인 파일**(README, yml)을 놓침
- "검증 완료"를 믿는다 → 뭘 검증했고 뭘 안 했는지 안 읽음 (h2-console은 검증 목록에 없었다)
- 익숙한 패턴과 다르면 "틀렸다" → "왜 다르지?"가 아니라 "빠졌다"
- 지시문의 애매한 단어("최신", "스프링 프레임워크")를 AI가 어떻게 해석했는지 확인 안 함

**교훈**
1. 검토는 diff **밖**에서 시작 — 영향받는데 안 바뀐 파일(README, 설정, CI)부터
2. "검증 완료"는 **무엇을**까지 읽는다. 안 적힌 건 안 한 것. 테스트가 안 건드리는 기능을 떠올린다
3. 지시문의 애매한 단어마다 AI가 뭘 골랐는지 묻는다
4. 의심이 들면 결론 내기 전에 **검색 한 번** (import 심볼), **모순 확인 한 번** (빌드가 됐는데 플러그인이 빠졌을 리가)
5. 요약본이 아니라 **실제 diff**를 본다 (주석에 이유가 적혀 있었다)

# 연습 기록

## #1 — 가장 많은 페이지를 본 사용자  (`MostActiveUser.java`)

**문제**: `"사용자 페이지"` 로그 배열에서 서로 다른 페이지를 가장 많이 본 사용자. 중복 페이지는 1번.

**내가 말한 접근법**
공백으로 나누고 → 사용자별로 묶고 → 같은 페이지는 하나로 합치고 → 개수 세서 최대. (흐름은 정확)

**막힌 곳**
- "같은 페이지를 하나로"를 어떤 자료구조로 → **Set**이 바로 안 나옴
- `computeIfAbsent` 처음 봄 → 이름으로 추측해서 맞힘 (`containsKey` + `put` 형태는 실무에서 본 적 있음)

**잘한 것**
- 전체 흐름을 코드 전에 말로 정리
- 모르는 걸 모른다고 바로 말함
- "왜 반복문이 두 개냐" → "첫 번째 안에서는 Set이 다 안 채워져서" 정확히 답함
- 복잡도 O(n) 맞힘

**보완**
- 엣지 케이스(빈 배열, 동점)를 먼저 묻지 않음
- 문제에 없는 조건("숫자만 뽑아서 정규화")을 추가함 → 문제를 단순하게 보기

## #2 — 회의실 예약 겹침  (`MeetingOverlap.java`)

**문제**: `{시작, 종료}` 배열에서 겹치는 예약이 하나라도 있으면 true. 조건을 일부러 애매하게 냄.

**내가 한 질문**
- "4개인데 왜 boolean 하나?" → 출력 형식 확인. 좋은 질문.
- "딱 붙은 건 겹친 건가?"를 **스스로 예상함** → 핵심 질문. `<` vs `<=`를 결정.
- 빈 배열 / 1개 / 정렬 여부는 못 물음

**내가 말한 접근법**
"b1 또는 b2가 a 안에 있으면 겹침" → **감싸는 경우(`a={10,11}, b={9,12}`)를 놓침.**
생각은 하고 있었는데 조건이 안 떠올라서 말 안 함 → 다음엔 "이 경우가 걸리는데 조건이 바로 안 떠오릅니다"라고 **말하기**.

**배운 것**
- 구간 겹침 표준 공식: `a1 < b2 && b1 < a2` — "안 겹치는 두 경우"의 부정에서 유도
- O(n²) → O(n log n): **시작 시각으로 정렬하면 바로 앞 것과만 비교**
- "O(n²)인데 빨라지려면?" → 정렬 아니면 HashMap

**잘한 것**
- 핵심 엣지 케이스(붙은 경우)를 스스로 떠올림
- (가)/(나) 중 짧은 쪽을 바로 고르고 "반대 부등호에 NOT"으로 정확히 요약
- `j = i+1` 이유, O(n²)이 문제라는 판단 정확

**보완**
- 엣지 케이스 질문이 1개로 끝남 → 체크리스트를 모든 명사에 기계적으로
- "정렬"이 바로 안 나옴

## #3 — 가장 많이 팔린 상품  (`BestSeller.java`)

**문제**: `"상품명 수량"` 주문 배열에서 수량 합계가 가장 큰 상품. 목표는 "코드 전에 엣지 케이스 3개 묻기".

**내가 한 질문** (코드 전에, 체크리스트 순서대로)
1. 빈 배열이거나 **null**이면? → ①
2. 주문이 하나뿐이면 그게 답? → ②
3. 수량·합계의 **최솟값·최댓값**은? → ③ (오버플로를 염두에 둔 질문. 면접관이 좋아함)
- 빠뜨린 것: **동점** → #1에 이어 두 번째. 체크리스트에 ★ 표시해 둠

**내가 말한 접근법**
- "Map" → "`Map<String, Integer>`, null이 올 수 있으니 int가 아니라 Integer" → "`getOrDefault`로 가져와서 더해서 put" → "다 넣고 반복문으로 부등호 비교"
- **힌트 없이 자료구조 → 메서드 → 흐름이 한 번에 이어짐** (#1에서 Set이 안 나왔던 것과 비교)
- 중간에 "Integer 말고 Double도 있나?" 확인하고 넘어감 — 좋은 습관

**함정 질문**: "`bestQty` 초기값 0인데 음수 수량이 섞이면?"
→ "0보다 커야 하는데 -1이라 `best = e.getKey()`가 안 들어가서 null 리턴" — **결과까지 정확히 추적**

**배운 것**
- `total.merge(name, qty, Integer::sum)` — `getOrDefault`+`put` 한 줄 버전
- max 초기값은 `0`이 아니라 `Integer.MIN_VALUE` 또는 "첫 번째 무조건 채택". 0을 쓴다면 **왜 안전한지 설명할 수 있어야** 함
- Map 메서드 3종 세트: `computeIfAbsent`(#1), `merge`(#3), `getOrDefault`

## #4 — 파일 경로 정리  (`SimplifyPath.java`)

**문제**: `"/home/user/./docs/../photos"` → `"/home/user/photos"`. 처음 보는 유형(Stack). 실무에서는 path traversal 방어 지점.

**문제 이해 단계**
- **"이 문제는 이해를 못 하겠다"를 바로 말함** → 면접관이 `cd` 비유로 재설명 → 손풀이 표로 확인
- "잘못된 경로를 고치는 코드인가?" → "아니, 같은 곳을 가리키는 가장 짧은 표현으로 줄이는 것(정규화)"
- 두 번째 예시 `/a/b/c/../../d` → `/a/d` 직접 도출 → 이해 확인

**내가 한 질문**
1. 경로 안에 **같은 이름의 폴더**가 있을 수 있나? → ③ 같은 값. **#1, #3에서 빠졌던 항목이 드디어 나옴**
2. 폴더 이름 **대소문자** 구분하나? → ③. Windows/Linux 차이로 실제 사고 나는 지점
3. `.`은 없애도 되나? → 규칙 재확인
4. (추가) 빈 경로·루트 위 `..`을 에러로 알려야 하지 않나? 경로는 누가 만드나(사람/프로그램/공격자)? → 전부 정당한 실무 질문
- 빠진 것: ① 빈 문자열 (#3에서는 물었는데 유형이 바뀌니 빠짐)
- 면접관이 보탠 함정: **루트에서 `..`** (`/../a` → `/a`), 연속 슬래시 (`/a//b/` → `/a/b`)

**내가 말한 접근법**
- "가장 최근에 넣은 걸 꺼낸다" → **"Queue"** → 정정: **Stack** (Queue는 정반대, 가장 먼저 넣은 것)
- 세 갈래 분기: `.`/빈 조각 무시, `..`은 pop, 그 외 push — 흐름은 정확 (`.` 설명이 살짝 섞였음)
- "빈 Stack에서 pop하면?" → "NPE인가? 잘 모르겠다" → `NoSuchElementException`, `isEmpty()`로 막기
- 복잡도 "O(2n)" → 상수 떼고 O(n)

**배운 것**
- `..` = 되돌리기 = Stack. Queue ↔ Stack은 정반대라 이름 틀리면 코드가 완전히 달라짐
- 빈 Stack pop은 Stack 문제의 단골 함정 (#3의 max 초기값과 같은 급)
- 엣지 케이스 질문 하나하나가 코드의 분기 하나하나가 됨 — `if (!stack.isEmpty())`, `sb.length() == 0 ? "/"`
- 자바에서 Stack은 `java.util.Stack` 대신 `ArrayDeque`

## #5 — 고객센터 상담 배정, 대기 시간  (`WaitingTimes.java`)

**문제**: 상담원 1명, FIFO 처리, 요청마다 처리 시간. 각 요청의 대기 시간. `{5,3,8}` → `{0,5,8}`. 실무 소재(홀수 회).

**내가 한 질문**
- "요청 배열에 뭘 물어야 할지 모르겠다" → **배열이면 무조건 ① 빈 것 ② 하나.** #3에서 물었는데 또 빠짐
- 처리 시간 음수·자릿수·오버플로 → ③ 좋음
- "요청이 취소되면?" → 범위(scope) 질문. 한 문장으로 짧게 — 깊이 조절 ✅. 다만 기본(①②) 없이 확장부터 나와 순서가 뒤집힘

**내가 말한 접근법**
- "먼저 들어온 것부터 → 배열 0번부터" → **"Queue"** ✅ 목표 달성 (#4의 혼동이 한 번에 잡힘)
- "반복문으로 더한다" ✅ + "시간 라이브러리로 분마다 뺀다" ✗ → **시뮬레이션과 산수 혼동.** 문제에 시계가 없으면 산수
- 대기 시간 = 앞사람들 처리 시간 합 → `elapsed` 변수 하나로 한 바퀴 = **누적 합**

**반전**: 코드에 Queue 객체가 없다. 배열 순회가 이미 FIFO. "개념은 Queue, 구현은 배열" — 이름 맞히기의 다음 단계는 "그 객체가 진짜 필요한가".

**수확**: **MQ로 금융 거래 부정 검사**를 만든 실무 경험이 나옴 → 6절 "경험 질문" 틀로 복원해 둘 것
